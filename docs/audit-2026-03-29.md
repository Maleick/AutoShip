## Critical (Must Fix)

### C1. Shared memory has no DACL — any process can read/write game state

**Files**: `dmft/src/ipc/shared.rs:48`, `dmft-dll/src/ipc/shared.rs:48`

Both reader and writer create shared memory with `None` security attributes (default DACL). Any process on the machine can open the predictable name `dmft_state_{pid}` and:
- **Read**: Extract all game state (spawn positions, player data).
- **Write**: Inject corrupt data that the orchestrator trusts.

The code has a TODO for this (`TODO(security-H2)`), but this is a critical gap for a 36-box setup where detection matters.

**Fix**: Create a restrictive DACL allowing only the current user SID. Randomize the shared memory name (pass it via the token file instead of deriving from PID).

---

### C2. Shared memory reader opens with PAGE_READWRITE instead of read-only

**File**: `dmft/src/ipc/shared.rs:53`

```rust
PAGE_READWRITE,  // ← should be PAGE_READONLY for the reader
```

The reader has write access to the shared memory. If the orchestrator has a bug, it could corrupt the DLL's data. This also violates the principle of least privilege.

**Fix**: Use `PAGE_READONLY` and `FILE_MAP_READ` on the reader side (the TODO at line 47 calls this out).

## High (Should Fix Soon)

### H1. Password not zeroized in `type_credentials_to_window` parameters

**File**: `dmft-dll/src/ipc/mod.rs:181-182`

The `StartLogin` handler passes `&password` (a `String` reference) to `type_credentials_to_window`. The `password` String lives on the IPC thread's stack until the function returns — it's not wrapped in `Zeroizing<>`. The `LoginFsm::Credentials` struct does zeroize on Drop, but the IPC handler holds a separate copy.

**Fix**: Use `Zeroizing<String>` for the password field in the `StartLogin` command variant, or zeroize the local copy after use.

### H2. `Credentials::Drop` zeroization is fragile

**File**: `dmft-dll/src/login/mod.rs:88-95`

```rust
unsafe {
    let bytes = self.password.as_bytes_mut();
    for b in bytes.iter_mut() { *b = 0; }
}
```

This zeroizes the String's current buffer, but `String::drop()` may not actually free the same buffer if the allocator has already moved it (e.g., after a realloc during `clone()`). Also, the compiler could optimize away the zeroing since the buffer is immediately freed.

**Fix**: Use the `zeroize` crate's `Zeroizing<String>` wrapper (already a dependency) which uses `ptr::write_volatile` to prevent optimization. Replace the custom Drop with `Zeroizing<String>`.

### H3. Session token fallback is PID-derived (predictable)

**File**: `dmft-dll/src/lib.rs:241-248`

When the orchestrator's CSPRNG token file is missing, the fallback generates a deterministic token from the PID:
```rust
*byte = pid_bytes[i % 4] ^ (i as u8);
```
A malicious process can compute this token and send commands to any EQ client. The warning log is good, but this path should be hardened.

**Fix**: Use `OsRng` as fallback instead of PID-derived bytes. Or refuse to start IPC without a valid token.

### H4. Named pipe has no authentication beyond session token

**Files**: `dmft-dll/src/ipc/pipe.rs`, `dmft/src/ipc/pipe.rs`

The named pipe uses a predictable name pattern (`dmft_cmd_{pid}`) with default security. Any local process can connect. The session token provides some protection, but the pipe itself should use a restrictive DACL.

**Fix**: Set a DACL on the pipe allowing only the current user SID.

### H5. `std::mem::forget(_guard)` leaks tracing worker thread

**File**: `dmft-dll/src/lib.rs:129`

The non-blocking tracing guard is leaked via `mem::forget` to keep it alive for the DLL's lifetime. This is documented and intentional, but means the background flush thread is never cleanly shut down. On DLL eject, pending log entries may be lost.

**Fix**: Store the guard in a `static OnceLock` and flush it in `graceful_shutdown()`.

### H6. `eject_dll` is unimplemented

**File**: `dmft/src/inject/loader.rs:127-131`

The eject function is a no-op stub:
```rust
pub fn eject_dll(pid: u32, dll_name: &str) -> Result<()> {
    // TODO: Find module handle in remote process, call FreeLibrary
    Ok(())
```

This means DLLs cannot be cleanly removed from EQ processes during development or hot-reload scenarios.

**Fix**: Implement `CreateToolhelp32Snapshot` → `Module32First/Next` → `CreateRemoteThread(FreeLibrary)`.

### H7. Atomic ordering inconsistencies in Enter World sequence

**File**: `dmft-dll/src/hooks/game_loop.rs:110-121`

`queue_enter_world` stores to 4 separate atomics with Release ordering, but there's no single fence or sequencing guarantee between them. The game loop thread reads them with Acquire. If the compiler or CPU reorders the stores, the game loop could see `ENTER_WORLD_STAGE=1` before the function addresses are visible.

**Fix**: Store the function addresses first, then store the stage last as the "commit" signal. Or use a `Mutex<Option<EnterWorldRequest>>` struct.

### H8. `#![allow(dead_code)]` on entire crates suppresses useful warnings

**Files**: `dmft-dll/src/lib.rs:4`, `dmft/src/main.rs:1`

Crate-level `#![allow(dead_code)]` hides genuinely unused code that should be cleaned up. The DLL may have legitimate reasons (exported functions), but `main.rs` should not need this.

**Fix**: Remove crate-level allows. Use targeted `#[allow(dead_code)]` on specific items that are intentionally unused (e.g., future expansion, cross-platform stubs).

## Medium (Should Fix)

### M1. 73 clippy warnings (40 collapsible-if, 5 is_multiple_of, etc.)

**Files**: Various (see `cargo clippy` output)

The most common issues:
- 40× collapsible `if` statements — could use `if let ... && condition`
- 5× manual `% == 0` instead of `.is_multiple_of()`
- 4× deprecated `GenericArray::from_slice` in crypto.rs
- 3× unneeded `return` statements
- 2× elidable lifetimes
- 1× `contains_key` + `insert` (use `entry()` API)
- 1× identical `if` blocks
- 1× function with 8 args (limit: 7)

**Fix**: Run `cargo clippy --fix` for auto-fixable issues. Manually review the rest.

### M2. `NPC` and `DPS` acronym naming

**Files**: `dmft/src/camp/puller.rs:12`, multiple files

Clippy flags `NPC` and `DPS` as fully-capitalized acronyms. Rust convention is `Npc`, `Dps`.

**Fix**: Rename to follow Rust conventions (or suppress with `#[allow(clippy::upper_case_acronyms)]` if the domain terms are strongly preferred).

### M3. 26 TODO comments in production code

**Files**: Various (see grep output)

Notable TODOs that should be tracked:
- `ipc/shared.rs`: Security DACL (covered by C1)
- `tui/app.rs:1670`: Hardcoded EQ path
- `tui/run.rs:635`: Commands not dispatched to clients
- `inject/loader.rs:128`: Eject DLL not implemented (covered by H6)
- `hooks/casting.rs`: Multiple unimplemented hooks (CastSpell, DoAbility, UseItem)
- `login/widgets.rs`: Several unvalidated vtable indices

**Fix**: Convert actionable TODOs to GitHub issues. Remove or document TODOs that are deferred to future milestones.

### M4. `clone()` called 123 times — some may be unnecessary

**Files**: Various

Many `.clone()` calls on Strings in the login chain (`ipc/mod.rs:187-188`, `login/mod.rs:152-153`) and camp/hunt modules. Not all are necessary — some can be replaced with references or `&str` borrows.

**Fix**: Profile the hot paths (game loop tick) and eliminate unnecessary clones. The login chain clones are one-time and acceptable.

### M5. `Mutex` poisoning handled inconsistently

**Files**: `dmft-dll/src/login/mod.rs:20-55`, `dmft-dll/src/hooks/game_loop.rs:169`

Some Mutex accesses use `unwrap_or_else(|e| e.into_inner())` (recover from poisoning), others use `lock().ok()` (silently ignore), and some use plain `.lock()` without handling.

**Fix**: Pick one strategy. For the DLL (which must not crash EQ), the `unwrap_or_else(into_inner)` pattern is correct — apply it consistently.

### M6. `CACHED_SPAWNS` static Mutex inside function body

**File**: `dmft-dll/src/hooks/game_loop.rs:360`

```rust
static CACHED_SPAWNS: Mutex<Vec<dmft_common::types::SpawnData>> = Mutex::new(Vec::new());
```

A static inside a function body is unusual and makes the cache harder to discover. It also means the Vec is never freed.

**Fix**: Move to module-level static alongside other statics for discoverability.

### M7. Login chain phase2 uses `thread::sleep` polling

**File**: `dmft-dll/src/ipc/mod.rs:213-258`

The login chain polls every 500ms with `thread::sleep`. While this was improved from hard sleeps, it still burns a thread that mostly sleeps. The FSM in `login/mod.rs` could drive this via game tick callbacks instead.

**Fix**: Low priority since this only runs during login (once per client launch), but the FSM approach is cleaner.

### M8. `read_spawn_data` has no bounds checking on memory reads

**File**: `dmft-dll/src/hooks/game_loop.rs:405-443`

Each field read (spawn ID, name, position, etc.) dereferences raw pointers with no bounds validation. If a spawn pointer is partially valid (e.g., freed memory), this causes UB.

**Fix**: Add a validity check before reading (e.g., check spawn_id != 0 as a canary, or use structured exception handling via Windows SEH).

### M9. `read_string_at` may read past allocation boundary

**File**: `dmft-dll/src/hooks/game_loop.rs:392-399`

```rust
let bytes = unsafe { std::slice::from_raw_parts(addr as *const u8, max_len) };
```

If `addr` points to valid memory but `max_len` exceeds the allocation, this is UB. The function assumes EQ's string fields are always at least `max_len` bytes (64 for names, 128 for zones).

**Fix**: Acceptable for known EQ struct layouts, but document the assumption explicitly.

### M10. Orchestrator-side pipe server not implemented

**File**: `dmft/src/ipc/pipe.rs`

The orchestrator pipe server likely needs the same security hardening as the DLL-side listener.

### M11. `login/widgets.rs` has multiple redundant CXWndManager scans

**File**: `dmft-dll/src/login/widgets.rs`

Functions like `write_login_credentials`, `type_credentials_to_window`, `click_button`, `is_window_visible` each independently resolve the CXWndManager and scan the window array. During login, this results in 5-10 redundant scans per tick.

**Fix**: Pass a resolved `CxWndContext` struct to avoid repeated scans.

### M12. `find_button_by_text` and `find_window_by_name` are near-duplicates

**Files**: `dmft-dll/src/ipc/mod.rs:422-448`, `dmft-dll/src/eq/widgets.rs:67-88`

`find_button_by_text` in `ipc/mod.rs` reimplements `find_window_by_name` from `eq/widgets.rs` with slightly different matching (exact vs case-insensitive).

**Fix**: Consolidate into a single search function with a match mode parameter.

### M13. `for_each_window` has different MAX_WINDOW_COUNT (2000 vs 500)

**File**: `dmft-dll/src/eq/widgets.rs:193` vs `eq/widgets.rs:45`

The `for_each_window` function uses `count > 2000` while other functions use `MAX_WINDOW_COUNT = 500`. This inconsistency could let corrupted data through.

**Fix**: Use `MAX_WINDOW_COUNT` consistently.

### M14. Deprecated `GenericArray::from_slice` in crypto

**File**: `dmft/src/credentials/crypto.rs:38,42,53,54`

The `aes_gcm` crate's `from_slice` is deprecated. Should upgrade to `generic-array` 1.x API.

**Fix**: Update to the non-deprecated constructor or bump the crate version.

### M15. `personality.rs` and `social.rs` clone frequently in Soul Engine

**Files**: `dmft/src/soul/personality.rs`, `dmft/src/soul/social.rs`

Soul Engine modules use many `String` clones for character names, personality traits, etc. Since these run on LLM request paths (not game ticks), performance impact is minimal but could be improved with `Arc<str>`.

**Fix**: Low priority — only matters if Soul Engine scales to high-frequency requests.

### L8. `Xorshift32` PRNG used for anti-detection jitter

`Xorshift32` is a minimal PRNG, which is fine for jitter timing. But the seed comes from system time, which is somewhat predictable. A CSPRNG would be more robust against timing analysis.

### L9. `set_edit_text_via_vtable` is dead code

**Files**: Various in `dmft-dll/src/login/widgets.rs`

Several offset calculations use raw hex values without named constants (e.g., `0x80`, `0x178`, `0x270`). Most are documented via comments, but named constants would improve readability.

### L12. `cargo test` reports 128 tests, CLAUDE.md says 621

**Fix**: Update CLAUDE.md to note this is the cross-platform total, or report the macOS-runnable count separately.

## Architecture Notes (Informational)

### Clean module boundaries ✓
The three crates have clear responsibilities:
- `dmft-common`: Shared types, offsets, protocol
- `dmft-dll`: Injected code (hooks, IPC writer, login, nav, combat)
- `dmft`: Orchestrator (TUI, IPC reader, config, credentials, launcher)

No circular dependencies detected. Cross-crate sharing is done through `dmft-common`.

### Thread safety model ✓
The DLL correctly identifies two threads:
1. **Game loop thread** (from `ProcessGameEvents` hook) — owns widget manipulation
2. **IPC listener thread** — receives commands, queues for game loop

Atomics bridge the two threads. The `queue_button_click` / `queue_enter_world` pattern is correct for scheduling UI operations from the IPC thread.

### Cross-platform strategy ✓
All Windows APIs are properly `#[cfg(windows)]`-gated with macOS stubs. The TUI runs on macOS with demo data. Build succeeds on both platforms.

### Credential handling ✓ (mostly)
- Argon2id key derivation with per-account salts — good
- AES-256-GCM encryption with random nonces — good
- `Zeroizing` wrapper on keys — good
- SQLite with parameterized queries — no SQL injection risk
- Master password never stored — good
- **Gap**: Password zeroization in DLL (see H1, H2)
