# Packet and Zoning Send-Path and State Ledger

This ledger is the curated packet/zoning intake surface for the current `M5` and `M6` work.

It exists to turn raw imports and repo-grounded code reading into explicit execution rules:

- which current control paths are already `In-process`
- which researched paths are only `Packet candidate`
- which protocol variants are currently `Blocked`

This file is an evidence ledger, not the roadmap source of truth. `docs/implementation-roadmap.md` remains canonical for milestone order, gates, and evidence-state rules.

## Status Labels

| Label | Meaning |
| --- | --- |
| `In-process` | The repo already has a concrete non-packet control path through EQ internals, widget interaction, memory writes, or `InterpretCmd`. |
| `Packet candidate` | Research points at a plausible packet path, but the repo does not yet have a validated sender, counter handling, or live-proof acceptance rule for it. |
| `Blocked` | A protocol shape or idea exists, but the repo does not currently dispatch it, or the risk/evidence bar is not high enough to treat it as supported. |

## Current Selection Rules

- Prefer the lowest-risk repo-grounded `In-process` path that already works.
- Do not treat imported packet notes as permission to bypass current control paths.
- Treat protocol variants that have no DLL dispatch arm as `Blocked`, even if the shared enum already defines them.
- Keep exploit-adjacent movement or travel claims provisional until `M6` and `M7` validation work exists.

## Current Safe Default Routing

| Operator or system intent | Route to prefer today | Why this is the default |
| --- | --- | --- |
| Start combat or sustain melee pressure | `CombatEngage` plus the existing combat FSM | This is the most complete repo-grounded path and already owns taunt, skills, disciplines, casts, and pet commands. |
| Move a client or set a camp spot | `NavigateTo`, `SetCamp`, `StopNavigation` | Navigation is implemented and observable today; direct move IPC and packet movement remain unbounded. |
| Run login, loot, accept, follow, or ad hoc operator commands | `SlashCommand` through `InterpretCmd` | The slash-command path is visible, already wired, and safer to reason about than speculative packet alternatives. |
| Send social or Soul Engine output | Keep it disabled or translate explicitly to `SlashCommand` in a future in-process pass | The higher-level chat enums exist, but they do not have a live DLL transport yet. |
| Zone or travel across boundaries | Stay on normal client/UI flows until `M6/#50` is complete | The research identifies candidate send paths, but current zoning work still lacks a validated state machine and recovery model. |

## Packet Send-Path Notes From Imports

The imported network notes currently point at this outbound shape:

1. game-specific helpers such as `Cmd_UseSkill`, `SendAttackPacketToServer`, `CEverQuest__SendZoneRequestPacket`, and `CEverQuest__SendEmoteOrSayPacket`
2. opcode scrambling
3. `NetworkSend` or, for some movement traffic, `UdpConnection::SendMessage`
4. socket transmission

Those notes are useful for naming likely packet candidate surfaces, but they do not remove three current blockers:

- the repo does not yet implement a general packet sender
- the imports call out anti-cheat counters that would need bounded handling
- the repo does not yet have live validation criteria strong enough to treat packet-first control as safe by default

## Current Conclusion

The repo is already rich in `In-process` control paths. The imported packet research is most useful right now as a validation and labeling source, not as a replacement for the existing control stack.

That means the current safe ordering is:

1. close obvious protocol-vs-dispatch gaps in the existing in-process surfaces
2. finish the zoning and ability validation ledgers
3. only then decide whether any packet candidate deserves promotion beyond research-backed status
